# Plugin Architecture — Design Spec

วันที่: 2026-08-13
สถานะ: รออนุมัติ
ที่มา: คำถามของผู้ใช้ — "อยากให้แอปเป็นแอปกลางแล้วเสียบฟีเจอร์เข้าไปเรื่อย ๆ คล้าย super app
วันหนึ่งอยากถอดออกต้องถอดได้สะอาด โดยมีศูนย์กลางเป็นระบบ user ที่มีอยู่แล้ว"

## เป้าหมาย

ทำให้ `null-app` เป็น **shell** ที่รับฟีเจอร์เข้ามาเสียบเป็นตัว ๆ โดยที่

1. เพิ่มฟีเจอร์ใหม่ = สร้างโฟลเดอร์ + เติมชื่อ 1 บรรทัด ไม่ต้องรื้อของเดิม
2. ถอดฟีเจอร์ออก = ลบโฟลเดอร์ + ลบ 1 บรรทัด + ลบ schema 1 คำสั่ง แล้วแอปยังคอมไพล์ผ่านทันที
3. ระบบ user ที่มีอยู่ (`auth.users` / `public.profiles` / `SessionStore` / `ProfileStore`) **ไม่ถูกแก้เลยแม้แต่บรรทัดเดียว**

ข้อ 3 ไม่ใช่ผลพลอยได้ แต่เป็นตัววัดว่า design ถูก — ระบบ user เป็นศูนย์กลางโดยการที่ฟีเจอร์พึ่งพามัน
ไม่ใช่โดยการที่มันต้องรู้จักฟีเจอร์

## นิยามของ "ถอดสะอาด" ที่วัดผลได้

คำว่าสะอาดต้องเป็นข้อความที่ผิดหรือถูกได้ ไม่ใช่ความรู้สึก ในเอกสารนี้แปลว่าครบทั้งสี่ข้อ:

1. หลังลบ `Features/<id>/` และลบ 1 บรรทัดใน `FeatureRegistry.swift` แล้ว
   **build ทั้ง iOS และ macOS ผ่านโดยไม่ต้องแก้ไฟล์อื่นแม้แต่ไฟล์เดียว**
2. `drop schema f_<id> cascade;` สำเร็จโดยไม่ชนกับวัตถุใด ๆ ของ core
3. ไฟล์และคีย์ที่ค้างอยู่ในเครื่องผู้ใช้เดิมถูกกวาดทิ้งเองตอนเปิดแอปครั้งถัดไป
4. `grep` ชื่อฟีเจอร์ทั้ง repo แล้วไม่เหลืออะไรนอกจากประวัติ git และ migration history

ข้อ 1 คือบททดสอบตัวจริง ถ้าต้องตามแก้ไฟล์อื่น แปลว่าเส้นแบ่งรั่วไปก่อนหน้านี้แล้ว

## ขอบเขต

อยู่ในขอบเขต:

- `Core/Feature.swift` — สัญญาที่ฟีเจอร์ต้องทำตาม
- `Core/FeatureRegistry.swift` — รายชื่อฟีเจอร์ที่ติดตั้งอยู่
- `Core/FeatureStorage.swift` — ที่เก็บของในเครื่อง + การกวาดของกำพร้า
- `HomeView` เปลี่ยนจากหน้าว่างเป็น grid ไอคอนที่อ่านจาก registry
- `Features/Example/` — ฟีเจอร์ตัวอย่างที่สร้างมาเพื่อถูกลบ ใช้พิสูจน์ทั้งระบบ
- กติกาการตั้งชื่อฝั่งฐานข้อมูลและ Storage สำหรับฟีเจอร์
- `UNINSTALL.md` เทมเพลตเดียวใช้ได้ทุกฟีเจอร์

ไม่อยู่ในขอบเขต (เลื่อนโดยตั้งใจ):

- **การเปิด/ปิดฟีเจอร์รายผู้ใช้จากเซิร์ฟเวอร์** — ยังไม่มีฟีเจอร์จริงสักตัวที่ต้องการ
- **ช่องทางให้ฟีเจอร์คุยกันเอง (event bus, shared service)** — ดูหัวข้อทางเลือกที่ปฏิเสธ
- **ระบบสิทธิ์ของฟีเจอร์** — ทุกฟีเจอร์อยู่ในไบนารีเดียวกันและเราเขียนเองทั้งหมด
- **deep link** — จองรูปแบบ `nullapp://f/<id>/…` ไว้เฉย ๆ ยังไม่สร้าง router
- **การโหลดโค้ดตอน runtime / mini-app แบบ WeChat** — App Store ไม่อนุญาต และผู้ใช้เลือกแนวทางโมดูลใน repo แล้ว
- **ให้ฟีเจอร์เข้าถึง `ProfileStore`** — เปิดทีหลังได้เสมอ ปิดทีหลังไม่ได้

## กฎเดียวที่ห้ามละเมิด

**การพึ่งพาวิ่งทางเดียว**

```
Features/Notes ──▶ Core ──▶ Storage (Session, Profile, Backend)
Features/Wallet ─┘
```

- ฟีเจอร์เรียก core ได้
- core เรียกฟีเจอร์ไม่ได้ ยกเว้นผ่าน `[any Feature]` ใน registry
- ฟีเจอร์เรียกกันเองไม่ได้

`FeatureRegistry.swift` จึงเป็น**ไฟล์เดียวในโปรเจกต์ที่เอ่ยชื่อฟีเจอร์ใด ๆ** ถ้าวันหนึ่งมีไฟล์ที่สองที่รู้จักชื่อฟีเจอร์
นั่นคือสัญญาณว่าเส้นแบ่งเริ่มรั่ว และเป็นจังหวะพิจารณาย้ายไปแนวทาง Swift Package (ดูท้ายเอกสาร)

## โครงไฟล์

```
null-app/
  Core/
    Feature.swift
    FeatureRegistry.swift
    FeatureStorage.swift
  Features/
    Example/
      ExampleFeature.swift
      Views/
      Storage/
      UNINSTALL.md
  Views/          ← shell เดิม: Home, Profile, Settings, SignUp
  Storage/        ← core เดิม: Backend, SessionStore, ProfileStore
  null_appApp.swift
```

ทุกไฟล์อยู่ใต้ `null-app/` ซึ่งเป็น synchronized file group อยู่แล้ว จึงสร้างไฟล์ด้วย Write ได้ตรง ๆ
**ห้ามแก้ `project.pbxproj` เพื่อลงทะเบียนไฟล์**

## สัญญา `Feature`

```swift
protocol Feature {
    /// namespace ของทุกอย่างที่ฟีเจอร์นี้เป็นเจ้าของ — DB schema, bucket, โฟลเดอร์, คีย์ UserDefaults
    /// ใช้ตัวพิมพ์เล็กและ _ เท่านั้น เพราะถูกเอาไปประกอบเป็นชื่อ schema ใน Postgres
    var id: String { get }

    /// ชื่อใต้ไอคอนบนหน้า Home
    var title: String { get }

    /// ชื่อ SF Symbol
    var systemImage: String { get }

    /// หน้าจอรากของฟีเจอร์ ถูก push จาก NavigationStack ของ Home
    func makeRoot(userID: UUID) -> AnyView
}
```

**ทำไมส่ง `userID` เป็นพารามิเตอร์ ไม่ให้ฟีเจอร์อ่านเองจาก `Backend.client.auth`**

การพึ่งพาโผล่อยู่ในลายเซ็น อ่านครั้งเดียวรู้ทันทีว่าฟีเจอร์ต้องการอะไรจาก core ทดสอบง่ายเพราะยัดค่าปลอมเข้าไปได้
และถ้าวันหนึ่งย้ายไป Swift Package แทบไม่ต้องแก้อะไร ส่วนการอ่านจาก singleton เองคือการพึ่งพาที่มองไม่เห็น
ซึ่งเป็นรอยรั่วชนิดเดียวกับที่ทำให้ระบบ plugin ถอดไม่ออกในระยะยาว

`AnyView` เป็นการแลกที่ตั้งใจ — เก็บ `[any Feature]` ไว้ใน array แล้วเรียก `makeRoot` ได้โดยไม่ต้องมี associated type
ต้นทุน type erasure ตรงนี้ไม่มีนัยสำคัญเพราะถูกเรียกครั้งเดียวตอน push หน้าจอ

## `FeatureRegistry`

```swift
enum FeatureRegistry {
    static let installed: [any Feature] = [
        ExampleFeature(),
    ]
}
```

การเพิ่มฟีเจอร์คือเติมหนึ่งบรรทัด การถอดคือลบหนึ่งบรรทัด ลำดับใน array คือลำดับไอคอนบนหน้า Home

## namespace ที่อนุมานจาก `id`

ห้ามตั้งชื่ออิสระ เพราะของที่ตั้งชื่ออิสระคือของที่วันถอดจะลืม

| ของ | ชื่อที่บังคับ | ตัวอย่างเมื่อ `id = "notes"` |
|---|---|---|
| Postgres schema | `f_<id>` | `f_notes` |
| Storage bucket | `f_<id>` | `f_notes` |
| โฟลเดอร์ในเครื่อง | `Application Support/Features/<id>/` | `…/Features/notes/` |
| คีย์ `UserDefaults` | `f.<id>.<key>` | `f.notes.sortOrder` |
| deep link (จองไว้) | `nullapp://f/<id>/…` | `nullapp://f/notes/…` |
| ชื่อ type ใน Swift | ขึ้นต้นด้วย `<Id>` | `NotesRowView` |

แถวสุดท้ายเป็นข้อบังคับ ไม่ใช่รสนิยม — แนวทางนี้อยู่ในโมดูล Swift เดียวกันทั้งหมด
ถ้าสองฟีเจอร์ประกาศ `RowView` เหมือนกันคือคอมไพล์ไม่ผ่าน

โฟลเดอร์ในเครื่องอยู่ที่ Application Support ไม่ใช่ Caches เพื่อให้ตรงกับ `ProfileStore` ที่เก็บ `profile.json`
ไว้ที่นั่นอยู่แล้ว การมีที่เก็บสองแบบแลกมาด้วยจุดกวาดสองจุด ซึ่งไม่คุ้ม

## ฝั่งฐานข้อมูล

**หนึ่งฟีเจอร์ = หนึ่ง Postgres schema** ชื่อ `f_<id>` นี่คือหัวใจของการถอดสะอาดฝั่งเซิร์ฟเวอร์
เพราะการลบทั้งฟีเจอร์ยุบเหลือ `drop schema f_notes cascade;`

กติกาประจำทุกตาราง:

- `user_id uuid not null references auth.users(id) on delete cascade`
  ผูกกับ `auth.users` **ไม่ใช่** `public.profiles` ตามโมเดล 3 ชั้นที่โปรเจกต์นี้แยกไว้แล้ว
  `profiles` จึงเปลี่ยนรูปได้โดยไม่ลากฟีเจอร์ไปด้วย
- เปิด RLS ทุกตาราง policy พื้นฐาน `user_id = auth.uid()` ครบทั้ง select / insert / update / delete
- **core ห้าม FK เข้าไปใน schema ของฟีเจอร์เด็ดขาด** — ทิศกลับกันคือสิ่งที่ทำให้ `drop schema … cascade`
  กลายเป็นคำสั่งที่ทำลาย core
- ฟีเจอร์อ่าน `public.profiles` ได้ (พึ่งพา core เป็นเรื่องปกติ) แต่ห้ามเขียน

`on delete cascade` ทำให้ **ไม่ต้องมี hook "ลบข้อมูลตอนผู้ใช้ลบบัญชี" ในทุกฟีเจอร์** — Postgres ถือ invariant นี้แทน

**ขั้นตอนที่ไม่ใช่ SQL:** Supabase เปิดให้ API เห็นเฉพาะ schema ที่อยู่ใน Exposed schemas
การติดตั้งฟีเจอร์จึงมีการตั้งค่าโปรเจกต์หนึ่งครั้ง และฝั่ง Swift ต้องเรียกผ่าน
`Backend.client.schema("f_notes").from("note")` ข้อดีคือขั้นตอนนี้จับคู่กับตอนถอดพอดี
(เอาชื่อออกจาก Exposed schemas) จึงไม่มีอะไรตกค้างแบบเงียบ ๆ

**ไฟล์:** ถ้าฟีเจอร์ต้องเก็บรูป ให้ใช้ bucket ของตัวเองชื่อ `f_<id>` ไม่ปนกับ `profile-images` ของ core
ถอดคือลบทั้ง bucket ซึ่งเลี่ยงกับดักที่บันทึกไว้แล้วว่าลบ `storage.objects` ด้วย SQL ไม่ได้
path ข้างในยังใช้ `user_id` **ตัวพิมพ์เล็ก** เหมือนเดิม

**migration:** ตั้งชื่อขึ้นต้นด้วย `f_<id>_` เพื่อให้ไล่ดูได้ว่าอันไหนเป็นของฟีเจอร์ไหน
ประวัติ migration จะยังมีร่องรอยของฟีเจอร์ที่ถอดไปแล้ว ซึ่งถูกต้อง — migration history
คือบันทึกว่าเกิดอะไรขึ้น ไม่ใช่ภาพสถานะปัจจุบัน

## `FeatureStorage` และการกวาดของกำพร้า

```swift
enum FeatureStorage {
    static func directory(for id: String) -> URL
    static func defaultsKey(_ id: String, _ key: String) -> String
    static func sweepOrphans()
}
```

`sweepOrphans()` ทำงานตอนเปิดแอป: ไล่ดูโฟลเดอร์ทั้งหมดใน `Application Support/Features/`
และคีย์ `UserDefaults` ทุกตัวที่ขึ้นต้นด้วย `f.` อันไหนที่ `id` ไม่อยู่ใน `FeatureRegistry.installed`
ให้ลบทิ้ง

นี่คือจุดที่ระบบ plugin ส่วนใหญ่พัง — ผู้ใช้ที่ลงแอปไว้ก่อนถอดจะมีของค้างอยู่ตลอดกาล
เพราะโค้ดที่เคยรู้จักมันถูกลบไปแล้ว ไม่เหลือใครลบให้ การตัดสินจาก registry ปัจจุบัน
ยังทำให้มันกวาดของจากฟีเจอร์ที่ถูกถอดไป *ก่อนที่ sweep จะมีอยู่* ได้ด้วย

**ไม่ทำงานใน `#if DEBUG`** เพราะการคอมเมนต์ registry ออกชั่วคราวเพื่อดีบักไม่ควรลบข้อมูลในเครื่องทิ้ง

## การเปลี่ยนแปลงกับโค้ดที่มีอยู่

| ไฟล์ | เปลี่ยนอะไร |
|---|---|
| `Views/HomeView.swift` | จาก "Nothing here yet" ตายตัว → grid ที่วนจาก `FeatureRegistry.installed`, empty state เหลือไว้สำหรับกรณี registry ว่าง, ปุ่ม Profile บน toolbar คงเดิม, รับ `userID` เข้ามาเพื่อส่งต่อให้ `makeRoot` |
| `null_appApp.swift` | `case .signedIn` เปลี่ยนเป็น `case .signedIn(let userID)` เพื่อส่งเข้า `HomeView` และเรียก `FeatureStorage.sweepOrphans()` ตอนเปิดแอป |

**ไม่แตะ:** `SessionStore`, `ProfileStore`, `Backend`, `RemoteProfile`, `Profile`,
`SignUpView`, `ProfileView`, `ProfileEditView`, `SettingsView` และทุกไฟล์ใน `Views/` ที่เหลือ

## ฟีเจอร์ตัวอย่างที่สร้างมาเพื่อถูกลบ

`Features/Example/` ใช้ครบทุกช่องทางของสัญญา เพื่อให้การถอดพิสูจน์ได้จริงไม่ใช่แค่ในทางทฤษฎี:

- หน้าจอที่เขียนและอ่านข้อมูลได้
- ตาราง `f_example.note` พร้อม RLS
- ไฟล์ใน `Application Support/Features/example/`
- คีย์ `f.example.<something>` ใน `UserDefaults`

หลังพิสูจน์เสร็จ ฟีเจอร์นี้จะถูกถอดออกตามขั้นตอนจริง และการถอดนั้นเองคือหลักฐาน

## ขั้นตอนถอด (`UNINSTALL.md` ใช้เทมเพลตนี้ทุกฟีเจอร์)

1. ลบโฟลเดอร์ `Features/<id>/`
2. ลบบรรทัดของฟีเจอร์ใน `Core/FeatureRegistry.swift`
3. build ทั้ง iOS และ macOS — **ต้องผ่านโดยไม่ต้องแตะไฟล์อื่น**
4. เอา `f_<id>` ออกจาก Exposed schemas (Project Settings → Data API)
5. `drop schema f_<id> cascade;`
6. ลบ bucket `f_<id>` (ถ้ามี) ผ่าน Storage API หรือ dashboard
7. ของค้างในเครื่องผู้ใช้ปล่อยให้ `sweepOrphans()` เก็บกวาดเอง

**ข้อ 4 ต้องมาก่อนข้อ 5 เสมอ และลำดับนี้กลับกันไม่ได้** — PostgREST สร้าง schema cache จากรายการ
Exposed schemas ถ้า schema ถูก drop ไปแล้วแต่ชื่อยังอยู่ในรายการ มันจะสร้าง cache ไม่ได้และตอบ
`PGRST002` กับ**ทุก** request ของโปรเจกต์ รวมถึงตารางของ core การถอดฟีเจอร์หนึ่งตัวจึงทำให้
ทั้งแอปใช้งานไม่ได้ จนกว่าจะมีคนไปแก้ค่าใน Dashboard — ซึ่งเป็นความเสียหายที่ใหญ่กว่าตัวฟีเจอร์
ที่ถอดออกหลายเท่า

ถ้าฟีเจอร์เก็บข้อมูลที่ผู้ใช้อาจอยากได้คืน `UNINSTALL.md` ของฟีเจอร์นั้นต้องมีคำสั่ง export
เขียนพร้อมใช้ไว้เหนือข้อ 5 — ข้อมูลถูกลบถาวรและกู้ไม่ได้

| `sweepOrphans()` | `swiftc` กับ harness โยนทิ้ง สร้างโฟลเดอร์และคีย์ของ id ปลอม | ของกำพร้าหาย และของที่อยู่ใน registry **ไม่หาย** |
| end-to-end | build → install → launch → เขียนข้อมูลจากหน้า Example | อ่านแถวจาก DB กลับมาเทียบ ไม่ตัดสินจากหน้าจอ |
| การถอด | เดินขั้นตอนถอดทั้ง 6 ข้อจริง | build ผ่านทั้งสองแพลตฟอร์มโดยไม่แตะไฟล์อื่น + `grep` ไม่เหลือร่องรอย |

แถวสุดท้ายคือการทดสอบที่มีค่าที่สุด เพราะมันทดสอบสถาปัตยกรรม ไม่ใช่โค้ด
และเป็นข้อเดียวที่ตอบคำถามตั้งต้นได้ตรง ๆ

## ทางเลือกที่ปฏิเสธ

**Swift Package แยกต่อฟีเจอร์** — คอมไพเลอร์จะบังคับเส้นแบ่งให้จริง ข้ามฝั่งไม่ได้เลยเพราะ `import` ไม่ผ่าน
ปฏิเสธเพราะ `CLAUDE.md` บันทึกไว้แล้วว่าการผูก package product เข้า target เป็นจุดที่พังเงียบ ๆ
(`grep` เจอ แต่ build ยังเจ๊ง) และต้องเปิด Xcode ตั้งค่าทุกครั้งที่เพิ่มฟีเจอร์ ซึ่งขัดกับ
synchronized file group ที่ทำให้สร้างไฟล์ใหม่ได้ฟรี ๆ อยู่ตอนนี้ — จ่ายต้นทุนนี้ตอนที่ยังไม่มีฟีเจอร์จริง
สักตัวไม่คุ้ม

**สัญญาถูกวางให้ย้ายไปแนวทางนี้ได้แบบกลไกล้วน** — `Core/` ไม่พึ่งพาอะไรนอกจากตัวเอง การย้ายคือย้ายไฟล์
ตัวชี้วัดว่าถึงเวลาแล้วคือจำนวนไฟล์ที่รู้จักชื่อฟีเจอร์มากกว่าหนึ่ง

**event bus / ให้ฟีเจอร์คุยกันเอง** — ปฏิเสธเพราะมันสร้างการพึ่งพาที่คอมไพเลอร์มองไม่เห็น
ฟีเจอร์ที่ฟัง event ของอีกตัวจะยังคอมไพล์ผ่านหลังอีกตัวถูกถอด แล้วเงียบไปเฉย ๆ ตอน runtime
ซึ่งทำลายเกณฑ์ "ถอดสะอาด" ข้อ 1 โดยที่ไม่มีอะไรเตือน วันที่ต้องการจริง ให้ยกขึ้นเป็นบริการของ core
อย่างชัดแจ้งแทน

**ระบบ manifest / เปิดปิดรายผู้ใช้ / ระบบสิทธิ์** — แก้ปัญหาที่ยังไม่มี ทุกฟีเจอร์อยู่ในไบนารีเดียวกัน
และเราเขียนเองทั้งหมด

**ตารางใน `public` ใช้คำนำหน้าแทน schema แยก** — ไม่ต้องตั้งค่า Exposed schemas ก็จริง
แต่การถอดกลายเป็นการไล่ `drop table` ทีละตัวจากความจำ ซึ่งเป็นสิ่งที่ spec นี้พยายามกำจัด

**tab bar** — เข้าถึงไวกว่า แต่เพดานอยู่ที่ราว 5 ตัว และจำนวน tab ที่เปลี่ยนไปทำให้โครงแอปกระตุกทุกครั้ง
ที่ถอดฟีเจอร์ grid บน Home รองรับจำนวนเท่าไรก็ได้และเพิ่ม/ถอดแล้วเลย์เอาต์ไม่กระทบ

**deep link ในรอบนี้** — การจด URL scheme ต้องใช้ `CFBundleURLTypes` ซึ่งเป็น array of dict
ที่ไม่เข้ากับวิธี `INFOPLIST_KEY_*` ที่โปรเจกต์นี้ใช้ (ไม่มี Info.plist) เท่ากับจ่ายความเสี่ยงฝั่ง Xcode
เพื่อของที่ยังไม่มีใครใช้

**mini-app โหลดตอน runtime แบบ WeChat** — App Store ไม่อนุญาตให้ดาวน์โหลดโค้ดที่ execute ได้
และการทำผ่าน WebView ต้องสร้าง bridge, sandbox, ระบบสิทธิ์ทั้งชุด ซึ่งใหญ่กว่าตัวแอปหลักหลายเท่า

## ข้อจำกัดที่รับรู้และยอมรับ

- **คอมไพเลอร์ไม่ได้บังคับเส้นแบ่ง** ฟีเจอร์ A เรียกโค้ดของฟีเจอร์ B ได้ในทางเทคนิค
  กันด้วยกติกาการตั้งชื่อ, โครงโฟลเดอร์ และรีวิว ทางแก้ที่บังคับได้จริงคือย้ายไป Swift Package
- **การถอดต้องเดินด้วยมือ** ไม่มีสคริปต์อัตโนมัติ เพราะสองในหกขั้นตอนอยู่ในหน้า dashboard ของ Supabase
- **การเพิ่มฟีเจอร์มีขั้นตอนนอก repo หนึ่งขั้น** คือเพิ่มชื่อ schema ใน Exposed schemas
