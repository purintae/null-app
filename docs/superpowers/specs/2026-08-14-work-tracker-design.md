# Work tracker — ฟีเจอร์แรกของ shell

วันที่ 14 ส.ค. 2026 · feature id `work` · schema `f_work`

## ทำไมต้องมี

null-app เป็น shell ที่มีระบบ user แล้ว แต่ registry ยังว่าง `f_example` ถูกติดตั้งแล้วถอดออก
เพื่อพิสูจน์ว่าการถอดสะอาดจริง สิ่งที่ยังไม่เคยพิสูจน์คือ **การติดตั้งของที่ตั้งใจให้อยู่ยาว**
และ **การมีสองฟีเจอร์อยู่ร่วมกัน**

ฟีเจอร์แรกจึงต้องเป็นของที่เจ้าของแอปใช้จริง ไม่ใช่ของสาธิต — เลือกเป็นการติดตามงาน
เพราะเป็นสิ่งที่ทำอยู่แล้วทุกวันด้วยมือ

## หน้าที่ของแอปนี้

ตอบคำถามเดียวให้ได้ทันทีที่เปิด: **"ตอนนี้ควรสนใจอะไร"**

ไม่ใช่ "มีงานอยู่กี่ชิ้น" — ตัวเลขนับของในคลังเปลี่ยนน้อยกว่าสัปดาห์ละครั้ง
พอไม่เปลี่ยน สายตาจะเลิกอ่านภายในสัปดาห์เดียว แล้วพื้นที่ดีที่สุดของหน้าจอก็เสียเปล่า

## โลกของงาน

การทำงานจริงมีลำดับแบบนี้ และโครงข้อมูลลอกตามนั้นตรง ๆ:

1. ต้นปีกำหนด Action Plan ว่าปีนี้มีโปรเจกต์อะไรบ้าง (แทรกกลางปีได้)
2. แต่ละโปรเจกต์ตี timeline ออกมา แบ่งเป็น stage พร้อมระยะเวลาของแต่ละ stage
3. ในแต่ละ stage มี task ย่อย

นอกจากโปรเจกต์ยังมี **Request** — งานสั้นกว่า เช่น แก้ bug บางจุด
Request **มี stage เหมือนกันทุกอย่าง แค่ timeline สั้นกว่า** จึงไม่ต้องมีทางแยกในโมเดลหรือในสูตรใด ๆ
ความต่างอยู่ที่ที่มา (Action Plan ประจำปี vs งานแทรก) ไม่ใช่ที่โครงสร้าง

```
item   (project | request)
  └─ stage   ชื่อ + ลำดับ + วันตามแผน + วันจริง
       └─ task   ชื่อ + เสร็จหรือยัง
```

## สิ่งที่คำนวณ ไม่เก็บ

คอลัมน์ที่เก็บค่าที่คำนวณได้ คือคอลัมน์ที่รอวันไม่ตรงกับความจริง ต่อไปนี้จึงไม่มีคอลัมน์:

### สถานะของ stage

| สถานะ | เงื่อนไข |
|---|---|
| Completed | มี `actual_end` |
| Current | มี `actual_start` แต่ไม่มี `actual_end` |
| Ahead | ไม่มี `actual_start` |

เพราะ stage ทับกันได้ **"stage ปัจจุบัน" จึงเป็นได้หลายอันพร้อมกัน** — UI ต้องเผื่อ

### ความคืบหน้าของ item

ถ่วงน้ำหนักตามความยาวของ stage ตามแผน ไม่ใช่นับ task ดิบ:

```
weight(s)      = planned_duration(s) / Σ planned_duration(ทุก stage ของ item)
completion(s)  = task ที่เสร็จ / task ทั้งหมดใน s
                 ถ้า s ไม่มี task เลย → 1 เมื่อมี actual_end, มิฉะนั้น 0
progress(item) = Σ weight(s) × completion(s)
```

**หารด้วยผลรวมความยาวทุก stage ไม่ใช่ความยาวปฏิทิน** — ในตัวอย่างจริงผลรวมคือ 11.25 เดือน
ขณะที่ช่วงปฏิทินคือ 10 เดือน (ส่วนต่างคือส่วนที่ทับกัน) ถ้าหารผิดตัว งานที่เสร็จครบจะได้ 112%
ซึ่งเป็นบั๊กที่โผล่ตอนโปรเจกต์ใกล้จบ — ช่วงที่คนดูเยอะที่สุดพอดี

### ช้าหรือเร็วกว่าแผน

```
planned_completion(s, วันนี้) = clamp((วันนี้ − planned_start) / (planned_end − planned_start), 0, 1)
planned_progress              = Σ weight(s) × planned_completion(s, วันนี้)
slip                          = planned_progress − progress
```

`slip` เป็นบวก = ช้ากว่าแผน แปลงเป็นจำนวนวันได้โดยคูณกับผลรวมความยาวทุก stage

### item เสร็จแล้วหรือยัง

ทุก stage มี `actual_end` = เสร็จ ไม่ต้องมีคอลัมน์ `status`

## หน้าจอ

### Overview — หน้าแรกของเมนู

**1 · บรรทัดสรุปพอร์ต** บรรทัดเดียว ไม่ใช่การ์ดสี่ใบ
> เดิน 5 · ช้ากว่าแผน 2

สองตัวนี้เปลี่ยนจริงและกระตุ้นให้ทำอะไรสักอย่าง

**2 · การ์ดงานที่กำลังเดิน** — พระเอกของหน้า

แต่ละใบมี: code + ชื่อ · แถบ stage ย่อ · stage ปัจจุบัน + badge · ช้า/เร็วกี่วัน · อัปเดตล่าสุด

แถบ stage ย่อคือ chip เรียงกัน (`RU RI D U PT PVT I`) กว้างตามระยะเวลา สีตามสถานะสามแบบ
กดการ์ดเพื่อเข้าไปดู timeline เต็ม

**3 · ช่วงนี้ควรโฟกัส** — task ที่ยังไม่เสร็จเฉพาะที่อยู่ใน stage ปัจจุบัน รวมทุก item ไม่เกิน 5–7 บรรทัด

**4 · เพิ่งขยับ** — 3–5 บรรทัดล่าสุด สำหรับ copy ไปวางใน status report

**ตัวกรอง** `ทั้งหมด` ตามด้วยประเภทที่ `work_type` ให้มา (วันนี้คือ Project และ Request)
default เป็นทั้งหมด เรียงตามความเร่งด่วน

งานที่เข้ากรุแล้วไม่ปรากฏในหน้านี้เลย ทั้งในการ์ดและในตัวนับ

### Timeline — หน้าแยก

Gantt เต็มแบบที่ทำในสไลด์: คอลัมน์ละเดือน แถวละ stage มีเส้น TODAY
**เลื่อนแนวนอนได้** เพราะ 7 stage × 10 เดือนยัดลงจอมือถือแล้วอ่านไม่ออก

### รายละเอียด item

ดูและแก้ทุกฟิลด์ รวมถึงจัดการ stage และ task

## ทางที่ปัดตก และเหตุผล

| ปัดตก | เหตุผล |
|---|---|
| การ์ด 2×2 นับจำนวน (Project / Request / Complete / In progress) | เป็นการนับของในคลัง ไม่ได้บอกว่าควรทำอะไร และเปลี่ยนช้าจนสายตาเลิกอ่าน |
| ตัวเลข Complete สะสม | ขึ้นอย่างเดียว ไม่มีวันลง ไม่เคยเรียกร้องให้ทำอะไร — เป็นรางวัล ไม่ใช่เครื่องมือ ถ้าอยากได้ให้ไปอยู่หน้าสรุปสิ้นเดือน |
| progress จากจำนวน task ดิบ | stage ที่มี task 3 อันกับ stage ที่มี 80 อัน ไม่ได้แปลว่าอันหลังสำคัญกว่า 26 เท่า — แผนบอกน้ำหนักอยู่แล้วผ่านความยาว stage |
| เก็บ `progress` เป็นคอลัมน์ | คำนวณได้ทุกเมื่อ การเก็บคือการเปิดช่องให้มันไม่ตรงกับ task |
| แถบ progress เส้นเดียวที่มีหมุด "อยู่ตรงนี้" | สมมติว่า stage เรียงต่อกันและมีตำแหน่งปัจจุบันจุดเดียว ซึ่งไม่จริง — stage ทับกันได้ |
| stage template ตายตัวทุกโปรเจกต์ | แต่ละโปรเจกต์กำหนด stage เอง การบังคับ template จะฝืนของจริง |
| ส่งออก Gantt เป็นภาพไปใช้ในสไลด์ | ทำสไลด์เองอยู่แล้ว การสร้างภาพเป็นงานใหญ่ที่ตัดได้ทั้งก้อน |
| แท็บ Project/Request เป็นตัวแบ่งหลัก | เคยเสนอให้ยุบเป็น filter รอง แต่ผู้ใช้แยกสองอย่างนี้ในหัวจริง (Action Plan vs งานแทรก) จึงเก็บไว้เป็นตัวกรองที่มองเห็นได้ |
| สัญญาณ "เงียบไปนาน" (ไม่มีอะไรขยับเกิน 14 วัน) | `updated_at` วัดการกรอกข้อมูล ไม่ได้วัดการทำงาน — ทำงานหนักทั้งสัปดาห์แต่ไม่เปิดแอปก็เข้าข่าย กลายเป็นการเตือนเรื่องพฤติกรรมของผู้ใช้เอง ยิ่งกว่านั้นบาง stage เงียบตามธรรมชาติ (ส่งให้ทีมอื่นแล้วรอ) และที่จำนวนงานราว 12 ชิ้นเจ้าของแอปจำได้เองอยู่แล้ว "ช้ากว่าแผน" ให้สัญญาณเดียวกันโดยวัดจากแผนที่ตีไว้จริง |

## แบ่งรอบ

รอบเล็กก่อน เพราะขั้นที่เจ็บที่สุดของการติดตั้งฟีเจอร์คือขั้นที่ MCP ทำแทนไม่ได้ —
ต้องเข้า Supabase Dashboard ไปเพิ่ม schema ใน **Exposed schemas** เอง
(ระวังช่อง **Extra search path** ที่อยู่ข้าง ๆ ใส่ผิดช่องแล้วเงียบ ไม่มี error)
เจอปัญหานั้นตอนมีโค้ดน้อย ถูกกว่าเจอตอนมีสามตาราง

| รอบ | ได้อะไร |
|---|---|
| 1 | เมนู `Work` โผล่บน Home กดเข้าไปเจอหน้าเปล่า — **UI ล้วน ไม่แตะเซิร์ฟเวอร์** ตัวกรองมีแค่ `ทั้งหมด` เพราะยังไม่มีที่มาของประเภท |
| 2 | schema + `work_type` + RLS + Exposed schemas + อ่านข้อมูลมาแสดงเป็นการ์ด — ใส่ข้อมูลผ่าน SQL ไปก่อน การ์ดยังไม่มี progress/slip เพราะยังไม่มี task |
| 3 | เพิ่ม/แก้ item และ stage ในแอป |
| 4 | task + progress ถ่วงน้ำหนัก + slip |
| 5 | หน้า Timeline เต็ม |

**รอบ 1 พิสูจน์เฉพาะครึ่ง Swift ของ install path** (registry, tile, navigation, การกวาดข้อมูลค้าง)
ครึ่งที่เสี่ยงกว่า — RLS และ Exposed schemas — ยังไม่ถูกแตะ และย้ายไปอยู่รอบ 2 อย่างรู้ตัว

## ความเสี่ยงที่รู้ตัว

**ต้นทุนตอนตั้งค่า** — stage กำหนดเองต่อโปรเจกต์ แปลว่าสร้างโปรเจกต์ใหม่ทีต้องใส่ stage
พร้อมวันที่ 4–7 บรรทัด นี่คือจุดที่คนเลิกใช้แอปประเภทนี้กันมากที่สุด ไม่ใช่ตอนใช้ แต่ตอนตั้งค่า
ทางบรรเทาที่ยังไม่ทำในรอบแรก ๆ: ก๊อป stage จากโปรเจกต์ก่อนหน้า

**ข้อมูลที่ไม่ถูกอัปเดตทำให้ทุกอย่างพัง** — ถ้าไม่ติ๊ก task แถบ progress จะแช่
แล้วทุกงานจะเข้าเกณฑ์ "ช้ากว่าแผน" หมด หน้าจอที่เตือนทุกอย่างเท่ากับไม่เตือนอะไรเลย
ทางแก้ไม่ใช่เอาระบบเตือนออก แต่ต้องทำให้การอัปเดตถูกมาก เช่น แก้ badge ได้จากหน้า Overview
โดยไม่ต้องเข้าไปข้างใน

## ภาษา

**ป้ายกำกับของแอปเป็นอังกฤษ ข้อความที่ผู้ใช้พิมพ์เป็นไทยได้** — `Work`, `Project`, `Request`,
`Timeline` คงเป็นอังกฤษตามม็อกอัพ ส่วนชื่องาน badge และชื่อ task รับภาษาไทยเต็มที่

ผลที่ตามมาซึ่งต้องระวังตั้งแต่รอบแรก: ภาษาไทยไม่มีช่องว่างระหว่างคำ การตัดบรรทัดจึงพึ่ง
พจนานุกรมของระบบ ไม่ใช่การหาช่องว่าง ข้อความไทยยาว ๆ ในการ์ดที่กว้างคงที่จึงตัดคำผิดที่
