# Work tracker — ฟีเจอร์แรกของ shell

วันที่ 14 ส.ค. 2026 · feature id `work` · schema `f_work`

## ทำไมต้องมี

null-app เป็น shell ที่มีระบบ user แล้ว แต่ registry ยังว่าง `f_example` ถูกติดตั้งแล้วถอดออก
เพื่อพิสูจน์ว่าการถอดสะอาดจริง สิ่งที่ยังไม่เคยพิสูจน์คือ **การติดตั้งของที่ตั้งใจให้อยู่ยาว**
และ **การมีสองฟีเจอร์อยู่ร่วมกัน**

ฟีเจอร์แรกจึงต้องเป็นของที่เจ้าของแอปใช้จริง ไม่ใช่ของสาธิต — เลือกเป็นการติดตามงาน
เพราะเป็นสิ่งที่ทำอยู่แล้วทุกวันด้วยมือ

## หน้าที่ของแอปนี้

ตอบคำถามเดียวให้ได้ทันทีที่เปิด: **"ตอนนี้ควรสนใจอะไร"**

ไม่ใช่ "มีงานอยู่กี่ชิ้น" — ตัวเลขนับของในคลังเปลี่ยนน้อยกว่าสัปดาห์ละครั้ง
พอไม่เปลี่ยน สายตาจะเลิกอ่านภายในสัปดาห์เดียว แล้วพื้นที่ดีที่สุดของหน้าจอก็เสียเปล่า

## โลกของงาน

การทำงานจริงมีลำดับแบบนี้ และโครงข้อมูลลอกตามนั้นตรง ๆ:

1. ต้นปีกำหนด Action Plan ว่าปีนี้มีโปรเจกต์อะไรบ้าง (แทรกกลางปีได้)
2. แต่ละโปรเจกต์ตี timeline ออกมา แบ่งเป็น stage พร้อมระยะเวลาของแต่ละ stage
3. ในแต่ละ stage มี task ย่อย

นอกจากโปรเจกต์ยังมี **Request** — งานสั้นกว่า เช่น แก้ bug บางจุด
Request **มี stage เหมือนกันทุกอย่าง แค่ timeline สั้นกว่า** จึงไม่ต้องมีทางแยกในโมเดลหรือในสูตรใด ๆ
ความต่างอยู่ที่ที่มา (Action Plan ประจำปี vs งานแทรก) ไม่ใช่ที่โครงสร้าง

```
item   (project | request)
  └─ stage   ชื่อ + ลำดับ + วันตามแผน + วันจริง
       └─ task   ชื่อ + เสร็จหรือยัง
```

## โครงข้อมูล

หนึ่งฟีเจอร์เป็นเจ้าของหนึ่ง schema — `f_work` — ทุกตาราง FK ไป `auth.users(id) on delete cascade`
ไม่ผูกกับ `public.profiles`

**ไม่มีคอลัมน์ `code` แยก** — รหัสงานพิมพ์นำหน้าชื่อไปเลย เพราะมันถูกใช้เป็นส่วนหนึ่งของชื่อ
ในการสื่อสารจริงอยู่แล้ว การแยกเป็นคอลัมน์จะได้ช่องบังคับกรอกเพิ่มมาหนึ่งช่อง
แลกกับความสามารถที่ยังไม่มีใครขอ

### การสร้างงาน — อะไรบังคับ อะไรไม่

**บังคับสองช่อง:** `type_code` และ `name`
**ไม่บังคับ:** `description`, `requested_by`, และ **stage ทั้งชุด**

เกณฑ์: ช่องบังคับคือช่องที่ไม่มีแล้วแอปทำงานไม่ได้จริง ๆ ไม่ใช่ช่องที่ควรมีข้อมูล
ช่องบังคับเป็นเหตุผลอันดับหนึ่งที่คนกดยกเลิกกลางฟอร์ม และ spec นี้จดความเสี่ยงไว้แล้วว่า
คนเลิกใช้แอปประเภทนี้ตอนตั้งค่า ไม่ใช่ตอนใช้ ถ้าบังคับใส่ stage ตั้งแต่สร้าง
ตัวอย่างจริงคือ 7 stage × 3 ช่อง = 21 ช่องก่อนกด Save ได้ครั้งแรก

**ผลที่ยอมรับ:** งานที่ยังไม่มี stage จะไม่ถูกนับในการ์ดสรุปทั้งสี่ใบ เพราะทั้งสี่คำนวณจาก
วันที่ของ stage การ์ดของงานนั้นขึ้นคำเชิญให้ใส่ timeline แทนแถบ stage —
เป็นแรงกระตุ้นที่ได้ผลกว่าการบังคับตั้งแต่หน้าสร้าง และไม่ปิดกั้นการจดงานไว้ก่อนเร็ว ๆ

**สิ่งที่พิจารณาแล้วไม่เก็บ:** ปีของ Action Plan (คำนวณจากวันเริ่มของ stage แรก),
ความสำคัญ/ลำดับ (คำนวณจากวันที่ — ใกล้กำหนดสุดและสายสุดขึ้นก่อน ไม่ต้องให้คนตัดสินแล้วลืมอัปเดต),
ลิงก์เอกสาร (หลายลิงก์ต่องานคือตารางอีกใบ เลื่อนไปรอบหลัง),
ระบบ/แอปที่เกี่ยวข้อง (ถ้าวันหนึ่งต้องมี ควรเป็นรายการที่คุมจากหลังบ้านเหมือน `work_type`
ไม่ใช่ช่องพิมพ์อิสระที่จะกลายเป็นชื่อเดียวกันสะกดสามแบบ)

**เข้ากรุก่อน ลบทีหลัง** — งานที่จบแล้วไม่หายไปเอง ผู้ใช้กด archive เมื่อพร้อม
งานที่เข้ากรุแล้วหลุดจาก Overview และจากตัวนับทุกตัว แต่ยังเปิดดูได้ในหน้ารายการที่เข้ากรุ
การลบถาวรเป็นการกระทำแยกที่ต้องตั้งใจ และเป็นทางเดียวที่ข้อมูลจะหายจริง —
ไม่มีที่ไหนในแอปที่ลบ item โดยอัตโนมัติ

## สิ่งที่คำนวณ ไม่เก็บ

คอลัมน์ที่เก็บค่าที่คำนวณได้ คือคอลัมน์ที่รอวันไม่ตรงกับความจริง ต่อไปนี้จึงไม่มีคอลัมน์:

### สถานะของ stage

| สถานะ | เงื่อนไข |
|---|---|
| Completed | มี `actual_end` |
| Current | มี `actual_start` แต่ไม่มี `actual_end` |
| Ahead | ไม่มี `actual_start` |

เพราะ stage ทับกันได้ **"stage ปัจจุบัน" จึงเป็นได้หลายอันพร้อมกัน** — UI ต้องเผื่อ

### ความคืบหน้าของ item

ถ่วงน้ำหนักตามความยาวของ stage ตามแผน ไม่ใช่นับ task ดิบ:

```
weight(s)      = planned_duration(s) / Σ planned_duration(ทุก stage ของ item)
completion(s)  = task ที่เสร็จ / task ทั้งหมดใน s
                 ถ้า s ไม่มี task เลย → 1 เมื่อมี actual_end, มิฉะนั้น 0
progress(item) = Σ weight(s) × completion(s)
```

**หารด้วยผลรวมความยาวทุก stage ไม่ใช่ความยาวปฏิทิน** — ในตัวอย่างจริงผลรวมคือ 11.25 เดือน
ขณะที่ช่วงปฏิทินคือ 10 เดือน (ส่วนต่างคือส่วนที่ทับกัน) ถ้าหารผิดตัว งานที่เสร็จครบจะได้ 112%
ซึ่งเป็นบั๊กที่โผล่ตอนโปรเจกต์ใกล้จบ — ช่วงที่คนดูเยอะที่สุดพอดี

### ช้าหรือเร็วกว่าแผน

วัดจากวันที่ ไม่ใช่จากสัดส่วน task:

```
overdue_stages = stage ที่ planned_end < วันนี้ และยังไม่มี actual_end
days_late      = วันนี้ − min(planned_end ของ overdue_stages)
```

`days_late` คือตัวเลขที่ขึ้นบนการ์ด ("ช้า 1 สัปดาห์") และเป็นเกณฑ์เดียวกับที่การ์ด Overdue นับ
— **ความช้ามีนิยามเดียวทั้งแอป** ถ้ามีสองนิยาม วันหนึ่งการ์ดจะบอกว่าช้าแต่ตัวนับบอกว่าไม่
แล้วไม่มีใครรู้ว่าอันไหนถูก

ทางเลือกที่ปัดตก: `planned_progress − progress` ซึ่งเทียบสัดส่วนงานที่เสร็จกับสัดส่วนเวลาที่ผ่านไป
แม่นกว่าในทางทฤษฎี แต่ต้องรอตาราง task และให้ผลผิดทันทีที่ผู้ใช้ไม่ได้ติ๊ก task ตามจริง

### item เสร็จแล้วหรือยัง

ทุก stage มี `actual_end` = เสร็จ ไม่ต้องมีคอลัมน์ `status`

## หน้าจอ

### Overview — หน้าแรกของเมนู

**1 · การ์ดสรุป 2×2**

| ใบ | นับ item ที่ยังไม่ archived ซึ่ง… |
|---|---|
| **Active** | เริ่มแล้ว (มี stage อย่างน้อยหนึ่งอันที่มี `actual_start`) และยังไม่เสร็จ |
| **Overdue** | มี stage ที่เลย `planned_end` มาแล้วแต่ยังไม่มี `actual_end` |
| **Due this month** | ยังไม่เสร็จ และ `planned_end` ของ stage สุดท้ายตกในเดือนปัจจุบัน |
| **Starting soon** | ยังไม่เริ่มเลย และ `planned_start` ของ stage แรกอยู่ภายใน **30 วัน** ข้างหน้า |

กติกาที่ทำให้สี่ใบนี้คุ้มพื้นที่: **ทุกใบตอบคนละคำถาม และไม่มีใบไหนคำนวณจากใบอื่นได้**
(Overdue เกือบทั้งหมดอยู่ใน Active ก็จริง แต่รู้ Active แล้วยังบอก Overdue ไม่ได้)
ทั้งสี่มองจากมุมเวลาคนละมุม — ตอนนี้ / เลยกำหนด / จะจบ / จะเริ่ม — และเปลี่ยนค่าทุกสัปดาห์

**Overdue วัดจากวันที่ ไม่ใช่จาก task** — ทางเลือกเดิมคือเทียบ `progress` กับ `planned_progress`
ซึ่งแม่นกว่าแต่ใช้ได้ต่อเมื่อ task ถูกติ๊กสม่ำเสมอ วิธีที่เลือกอ่านจากข้อมูลที่มีอยู่แล้ว
ไม่ขอความขยันเพิ่มจากผู้ใช้ และใช้ได้ตั้งแต่รอบที่ยังไม่มีตาราง task

**ไม่มีระยะผ่อนผัน** — เลยกำหนดมาวันเดียวก็นับ เพราะคำว่า overdue หมายความอย่างนั้น
ถ้าตั้งเกณฑ์เป็น 7 วัน คำกับความหมายจะไม่ตรงกันและต้องมีคำอธิบายกำกับ
ถ้าใช้จริงแล้วรกเกินไปค่อยเติมระยะผ่อนผันทีหลัง

**ทุกใบต้องกดได้** กดแล้วรายการข้างล่างกรองเหลือเฉพาะกลุ่มนั้น
การ์ดที่กดไม่ได้เป็นแค่ป้าย ส่วนการ์ดที่กดได้เป็นเครื่องมือ — และนี่คือเงื่อนไขที่ทำให้
การ์ดชุดนี้ต่างจากชุดที่เคยถูกปัดตก ไม่ใช่แค่หัวข้อที่เปลี่ยนไป

เกณฑ์ 7 วันและ 30 วันเป็นค่าตั้งต้นที่ยังไม่ได้ทดสอบกับของจริง

**2 · การ์ดงานที่กำลังเดิน** — พระเอกของหน้า

แต่ละใบมี: ชื่อ (มีรหัสงานนำหน้าอยู่แล้ว) · แถบ stage ย่อ · stage ปัจจุบัน + badge ·
ช้า/เร็วกี่วัน · อัปเดตล่าสุด

งานที่ยังไม่มี stage จะแสดงคำเชิญให้ใส่ timeline แทนแถบ stage และไม่มีตัวเลขช้า/เร็ว

แถบ stage ย่อคือ chip เรียงกัน (`RU RI D U PT PVT I`) กว้างตามระยะเวลา สีตามสถานะสามแบบ
กดการ์ดเพื่อเข้าไปดู timeline เต็ม

**3 · ช่วงนี้ควรโฟกัส** — task ที่ยังไม่เสร็จเฉพาะที่อยู่ใน stage ปัจจุบัน รวมทุก item ไม่เกิน 5–7 บรรทัด

**4 · เพิ่งขยับ** — 3–5 บรรทัดล่าสุด สำหรับ copy ไปวางใน status report

**ตัวกรอง** `ทั้งหมด` ตามด้วยประเภทที่ `work_type` ให้มา default เป็นทั้งหมด

**ห้ามใช้ segmented picker** — มันแบ่งความกว้างเท่ากันแบบตายตัวและเลื่อนไม่ได้ พอมีประเภทที่ห้า
ตัวอักษรจะถูกบีบจนอ่านไม่ออก และรูปทรงของมันสื่อว่าตัวเลือกมีเท่านี้ ซึ่งขัดกับการที่
`work_type` เพิ่มได้จากหลังบ้าน ใช้ **chip เรียงแนวนอนที่เลื่อนได้** แทน — รับจำนวนเท่าไหร่ก็ได้
และการเลื่อนได้ก็บอกตัวเองว่ายังมีต่อ

งานที่เข้ากรุแล้วไม่ปรากฏในหน้านี้เลย ทั้งในการ์ดและในตัวนับ

### รายละเอียด item

ดูและแก้ทุกฟิลด์ รวมถึงจัดการ stage และ task

## ทางที่ปัดตก และเหตุผล

| ปัดตก | เหตุผล |
|---|---|
| หัวข้อเดิมของการ์ด 2×2 (Project / Request / Complete / In progress) | เป็นการนับของในคลัง ไม่ได้บอกว่าควรทำอะไร และเปลี่ยนช้าจนสายตาเลิกอ่าน — **สิ่งที่ถูกปัดตกคือหัวข้อสี่ตัวนี้ ไม่ใช่รูปแบบ 2×2** ตัวกริดถูกนำกลับมาแล้วพร้อมหัวข้อชุดใหม่ที่กดกรองได้ |
| บรรทัดสรุปบรรทัดเดียวแทนกริด (`เดิน 5 · ช้ากว่าแผน 2`) | เสนอไว้ตอนที่กริดถูกปัดตกทั้งใบ พอกริดกลับมาพร้อมหัวข้อที่กดได้ บรรทัดนี้ก็ให้ข้อมูลน้อยกว่าโดยไม่ได้ประหยัดที่มากพอจะคุ้ม |
| ตัวเลข Complete สะสม | ขึ้นอย่างเดียว ไม่มีวันลง ไม่เคยเรียกร้องให้ทำอะไร — เป็นรางวัล ไม่ใช่เครื่องมือ ถ้าอยากได้ให้ไปอยู่หน้าสรุปสิ้นเดือน |
| progress จากจำนวน task ดิบ | stage ที่มี task 3 อันกับ stage ที่มี 80 อัน ไม่ได้แปลว่าอันหลังสำคัญกว่า 26 เท่า — แผนบอกน้ำหนักอยู่แล้วผ่านความยาว stage |
| เก็บ `progress` เป็นคอลัมน์ | คำนวณได้ทุกเมื่อ การเก็บคือการเปิดช่องให้มันไม่ตรงกับ task |
| แถบ progress เส้นเดียวที่มีหมุด "อยู่ตรงนี้" | สมมติว่า stage เรียงต่อกันและมีตำแหน่งปัจจุบันจุดเดียว ซึ่งไม่จริง — stage ทับกันได้ |
| stage template ตายตัวทุกโปรเจกต์ | แต่ละโปรเจกต์กำหนด stage เอง การบังคับ template จะฝืนของจริง |
| ส่งออก Gantt เป็นภาพไปใช้ในสไลด์ | ทำสไลด์เองอยู่แล้ว การสร้างภาพเป็นงานใหญ่ที่ตัดได้ทั้งก้อน |
| แท็บ Project/Request เป็นตัวแบ่งหลัก | เคยเสนอให้ยุบเป็น filter รอง แต่ผู้ใช้แยกสองอย่างนี้ในหัวจริง (Action Plan vs งานแทรก) จึงเก็บไว้เป็นตัวกรองที่มองเห็นได้ |
| สัญญาณ "เงียบไปนาน" (ไม่มีอะไรขยับเกิน 14 วัน) | `updated_at` วัดการกรอกข้อมูล ไม่ได้วัดการทำงาน — ทำงานหนักทั้งสัปดาห์แต่ไม่เปิดแอปก็เข้าข่าย กลายเป็นการเตือนเรื่องพฤติกรรมของผู้ใช้เอง ยิ่งกว่านั้นบาง stage เงียบตามธรรมชาติ (ส่งให้ทีมอื่นแล้วรอ) และที่จำนวนงานราว 12 ชิ้นเจ้าของแอปจำได้เองอยู่แล้ว "ช้ากว่าแผน" ให้สัญญาณเดียวกันโดยวัดจากแผนที่ตีไว้จริง |

## แบ่งรอบ

รอบเล็กก่อน เพราะขั้นที่เจ็บที่สุดของการติดตั้งฟีเจอร์คือขั้นที่ MCP ทำแทนไม่ได้ —
ต้องเข้า Supabase Dashboard ไปเพิ่ม schema ใน **Exposed schemas** เอง
(ระวังช่อง **Extra search path** ที่อยู่ข้าง ๆ ใส่ผิดช่องแล้วเงียบ ไม่มี error)
เจอปัญหานั้นตอนมีโค้ดน้อย ถูกกว่าเจอตอนมีสามตาราง

| รอบ | ได้อะไร |
|---|---|
| 1 | เมนู `Work` โผล่บน Home กดเข้าไปเจอหน้าเปล่า — **UI ล้วน ไม่แตะเซิร์ฟเวอร์** ตัวกรองมีแค่ `ทั้งหมด` เพราะยังไม่มีที่มาของประเภท |
| 2 | schema + `work_type` + RLS + Exposed schemas + อ่านข้อมูลมาแสดงเป็นการ์ด — ใส่ข้อมูลผ่าน SQL ไปก่อน ตัวนับทั้งสี่ใบและ `days_late` ใช้ได้ครบตั้งแต่รอบนี้เพราะคำนวณจากวันที่ ส่วน progress % ยังไม่มีเพราะยังไม่มี task |
| 3 | เพิ่ม/แก้ item และ stage ในแอป |
| 4 | task + progress ถ่วงน้ำหนักตามความยาว stage |
| 5 | หน้า Timeline เต็ม |

**รอบ 1 พิสูจน์เฉพาะครึ่ง Swift ของ install path** (registry, tile, navigation, การกวาดข้อมูลค้าง)
ครึ่งที่เสี่ยงกว่า — RLS และ Exposed schemas — ยังไม่ถูกแตะ และย้ายไปอยู่รอบ 2 อย่างรู้ตัว

## ความเสี่ยงที่รู้ตัว

**ต้นทุนตอนตั้งค่า** — stage กำหนดเองต่อโปรเจกต์ แปลว่าสร้างโปรเจกต์ใหม่ทีต้องใส่ stage
พร้อมวันที่ 4–7 บรรทัด นี่คือจุดที่คนเลิกใช้แอปประเภทนี้กันมากที่สุด ไม่ใช่ตอนใช้ แต่ตอนตั้งค่า
ทางบรรเทาที่ยังไม่ทำในรอบแรก ๆ: ก๊อป stage จากโปรเจกต์ก่อนหน้า

**ข้อมูลที่ไม่ถูกอัปเดตทำให้ทุกอย่างพัง** — ถ้าไม่ติ๊ก task แถบ progress จะแช่
แล้วทุกงานจะเข้าเกณฑ์ "ช้ากว่าแผน" หมด หน้าจอที่เตือนทุกอย่างเท่ากับไม่เตือนอะไรเลย
ทางแก้ไม่ใช่เอาระบบเตือนออก แต่ต้องทำให้การอัปเดตถูกมาก เช่น แก้ badge ได้จากหน้า Overview
โดยไม่ต้องเข้าไปข้างใน

**ระบบเตือนเก่งเฉพาะตอนงานเยอะ** — ที่ประมาณ 12 ชิ้นเจ้าของแอปจำได้เองอยู่แล้ว
บล็อก "ช่วงนี้ควรโฟกัส" จะมีค่าจริงตอนงานเกิน ~30 ชิ้น หรือตอนกลับมาจากลาพักร้อน
เหตุผลข้อเดียวกันนี้คือที่มาของการตัดสัญญาณ "เงียบไปนาน" ออกไปแล้ว

`Timeline` คงเป็นอังกฤษตามม็อกอัพ ส่วนชื่องาน badge และชื่อ task รับภาษาไทยเต็มที่
