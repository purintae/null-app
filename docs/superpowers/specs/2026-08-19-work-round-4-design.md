# Work tracker รอบ 4 — task เป็นตัวปิด stage

ต่อจาก `2026-08-14-work-tracker-design.md` เอกสารนี้เขียนเฉพาะสิ่งที่**เปลี่ยน**
และสิ่งที่**เพิ่ม** ส่วนที่ไม่ได้พูดถึงให้ถือตามสเปกเดิม

รอบ 3 ทำให้สร้างงานและแบ่ง stage ได้จากในแอป สิ่งที่ยังทำไม่ได้คือบอกว่างานนั้น
**ไปถึงไหนแล้ว** — วันนี้ต้องกดสวิตช์ `Started` / `Finished` เอง ซึ่งเป็นการรายงาน
ความคืบหน้าด้วยการจำว่าต้องรายงาน รอบนี้เปลี่ยนให้ความคืบหน้าเป็นผลข้างเคียงของการทำงานจริง

## คำที่ตกลงกันแล้ว

| คำ | หมายถึง |
|---|---|
| **Task** | งานย่อยใน stage หนึ่งอัน มีชื่อและสถานะเสร็จ/ไม่เสร็จ |
| **ปิด stage** | task ทุกอันใน stage นั้นเสร็จครบ — **ไม่ใช่การกดปุ่ม** |
| **Freeze** | สภาพที่ stage ถัดไปยังเริ่มไม่ได้เพราะ stage ก่อนหน้ายังไม่ปิด — เป็นผลที่เกิดเอง ไม่ใช่สถานะที่เก็บ |
| **Baseline** | แผนแรกที่ตั้งไว้ตอนสร้าง เก็บไว้เทียบ ไม่ถูกเขียนทับเมื่อเลื่อน |

## สิ่งที่เปลี่ยนจากสเปกเดิม

| เดิม | ใหม่ | เหตุผล |
|---|---|---|
| `stage.actual_start` | **ตัดทิ้ง** | ในกระบวนการจริง stage เริ่มตามวันที่กำหนดเสมอ พอเริ่มไม่ได้ตามแผน สิ่งที่เกิดขึ้นคือ**เลื่อน timeline** ไม่ใช่บันทึกส่วนต่าง คอลัมน์นี้จึงไม่มีทางต่างจาก `planned_start` ได้เลย |
| `stage.actual_end` | **ตัดทิ้ง** คำนวณจาก task แทน | สเปกเดิมเขียนไว้เองว่า "คอลัมน์ที่เก็บค่าที่คำนวณได้ คือคอลัมน์ที่รอวันไม่ตรงกับความจริง" — วันปิด stage คือวันที่ติ๊ก task ตัวสุดท้าย ซึ่งอ่านจาก `task.done_at` ได้ตรง ๆ |
| สวิตช์ `Started` / `Finished` | **ไม่มี** | ไม่มีคอลัมน์ให้กดแล้ว และการแก้ผิดมีทางกลับอยู่แล้วคือติ๊ก task ออก |
| Overdue = ทุก stage ที่เลยกำหนดและยังไม่ปิด | **เฉพาะ stage แรกที่ยังไม่ปิด** | ดูหัวข้อ Freeze |
| `planned_*` เป็นแผนเดียว | `planned_*` = แผนปัจจุบัน + `baseline_*` = แผนแรก | เลื่อนแล้วต้องยังตอบได้ว่าหลุดจาก Action Plan ต้นปีไปเท่าไหร่ |

**บันทึกไว้เพื่อไม่ให้เข้าใจผิดว่ามักง่าย:** รอบ 3 มีบั๊กที่สวิตช์ทั้งสองตัวกดปิดไม่ได้
ไล่หาสาเหตุแล้วตัดตัวแปรออกได้สี่อย่าง (`DisclosureGroup`, การอยู่ติด `DatePicker`,
การอยู่คอนเทนเนอร์เดียวกัน, binding ที่ผูกกับตำแหน่งใน array) ยังไม่พบสาเหตุ
การตัดสินใจลบสวิตช์**ไม่ได้เกิดเพราะซ่อมไม่ได้** — เหตุผลข้างบนยืนอยู่ได้เองแม้สวิตช์จะทำงานปกติ
แต่บั๊กนั้นทำให้ไม่ต้องลังเลว่าจะซ่อมหรือลบ รายละเอียดอยู่ใน
`.superpowers/sdd/2026-08-18-work-round-3/progress.md`

## โครงข้อมูล

### `f_work.task` — ตามสเปกเดิม ยืนยันไม่เปลี่ยน

| คอลัมน์ | ชนิด | หมายเหตุ |
|---|---|---|
| `id` | uuid PK | |
| `stage_id` | uuid | → `stage(id) on delete cascade` |
| `title` | text | ห้ามว่าง — check constraint แบบเดียวกับ `stage.name` |
| `done_at` | timestamptz, null ได้ | null = ยังไม่เสร็จ |
| `position` | int | ลำดับที่แสดง มาจากตำแหน่งในรายการ ไม่ใช่ช่องให้กรอก |
| `created_at` / `updated_at` | timestamptz | |

RLS สืบเจ้าของผ่าน `stage` → `work` → `user_id` สองชั้น เขียน policy ด้วย `exists`
แบบเดียวกับที่ `stage` ทำอยู่ และ **ต้องมี `with check` ในทั้ง insert และ update**
ไม่งั้นย้าย task ไปแขวนใต้ stage ของคนอื่นได้

### `f_work.stage` — คอลัมน์ที่เปลี่ยน

| คอลัมน์ | เปลี่ยนเป็น |
|---|---|
| `actual_start` | **drop** |
| `actual_end` | **drop** |
| `baseline_start` / `baseline_end` | **เพิ่ม** date, not null — เขียนครั้งเดียวตอน insert ไม่แตะอีกตลอดชีวิตของแถว |

`stage_actual_dates_ordered` หายไปพร้อมคอลัมน์ ส่วน `stage_dates_ordered` อยู่ต่อ
และเพิ่มคู่แฝดของมันสำหรับ baseline

### การย้ายข้อมูลเดิม — ต้องทำก่อน drop

`26-BP-07-02` มี stage ที่ปิดไปแล้วจริงและวันปิดอยู่ใน `actual_end` ถ้า drop ตรง ๆ
ประวัติหายทั้งหมด ก่อน drop ต้องแปลง stage ที่มี `actual_end` เป็น task หนึ่งอัน:

```
title   = 'ปิด stage'      (หรือชื่อ stage นั้น)
done_at = actual_end
```

แล้ว stage นั้นจะยังอ่านว่าปิดแล้วเหมือนเดิมภายใต้กติกาใหม่ ส่วน `baseline_*`
ของแถวเดิมทั้งหมด backfill เท่ากับ `planned_*` ณ วันย้าย — แผนแรกที่บันทึกทันคือแผน ณ วันนี้

## กติกา

### ปิด stage

stage ปิดเมื่อ **มี task อย่างน้อยหนึ่งอัน และทุกอันมี `done_at`**

วันปิด = `max(done_at)` ของ task ใน stage นั้น

**stage ที่ไม่มี task เลยจะปิดไม่ได้ตลอดกาล — ตั้งใจให้เป็นแบบนี้** ไม่ใช่ลืมกรณีนี้
เพราะ "ทุก task เสร็จ" กับ "ไม่มี task เลย" ต่างกันคนละเรื่อง แต่ถ้าใช้กติกา
`task ที่ยังไม่เสร็จ = 0` เฉย ๆ สองอันนี้จะให้ผลเหมือนกัน แล้ว stage ที่เพิ่งสร้าง
จะกลายเป็น "เสร็จแล้ว" ทันทีตั้งแต่วินาทีแรก

ผลที่ยอมรับ: ทุก stage ต้องมี task อย่างน้อยหนึ่งอันเสมอ ซึ่งบังคับให้เขียนออกมาว่า
**อะไรคือของที่ต้องได้จาก stage นี้** — RU จะมี task ว่า `user ออก proposal`
ซึ่งตรงกับที่กระบวนการจริงใช้ตัดสินว่า stage นั้นจบหรือยังอยู่แล้ว

### Overdue มีได้ทีละอัน

> **stage ที่ขึ้น Overdue คือ stage แรกที่ยังไม่ปิด และเลย `planned_end` มาแล้ว
> — งานหนึ่งชิ้นมีได้ไม่เกินหนึ่งอัน**

นี่คือทั้งหมดของ Freeze ไม่ต้องมีคอลัมน์ ไม่ต้องมีปุ่มแช่แข็ง/ปลดแช่แข็ง

เหตุผล: ถ้า RU ค้างเพราะ user ยังไม่ออก proposal แล้ว stage อีกสี่อันข้างหลังก็เลยวัน
ตามแผนไปด้วย แอปแบบเดิมจะขึ้นว่า overdue 5 อัน ทั้งที่ความจริงมีปัญหาอยู่จุดเดียว
อีกสี่อันไม่มีใครผิด มันแค่ยังไม่ถึงคิว — ตัวเลขที่เกินความจริงบ่อย ๆ คือตัวเลขที่คนเลิกเชื่อทั้งใบ

และปุ่มแช่แข็งที่ต้องกดเองคือปุ่มที่วันหนึ่งจะลืมกด แล้วตัวเลขก็จะโกหกอีกแบบหนึ่ง

### การเลื่อนเมื่อปิด stage ช้า

เมื่อ stage ปิด ถ้าวันปิด **ช้ากว่า** `planned_end`:

```
delta = วันปิด − planned_end
stage ทุกอันที่ position มากกว่า และยังไม่ปิด → planned_start/end บวก delta
```

**เลื่อนทุกอันด้วยจำนวนวันเท่ากัน ไม่ใช่ต่อท้ายตัวก่อนหน้าทีละอัน** — สเปกเดิมระบุว่า
stage ทับกันได้ (PT คาบ SIT & UAT, IMP คาบ PVT) การไล่ต่อท้ายจะดึงของที่ตั้งใจให้ทับ
มาเรียงเป็นแถวเดี่ยว ผลลัพธ์เหมือนกันเป๊ะเมื่อ stage เรียงต่อกันอยู่แล้ว

**ปิดเร็วกว่าแผนไม่ดึงอะไรขึ้นมา** (`delta < 0` ไม่ทำอะไร) เพราะการที่เราเสร็จก่อน
ไม่ได้แปลว่าทีมถัดไปว่างรับงานเร็วขึ้น การดึงแผนขึ้นเองจะสร้างวันที่ไม่มีใครตกลงด้วย

การเลื่อนนี้**เขียนทับ `planned_*`** ซึ่งคือเหตุผลทั้งหมดที่ต้องมี `baseline_*`

### ความช้าอ่านได้สองแบบ

| เทียบกับ | ตอบคำถาม |
|---|---|
| `planned_*` (แผนปัจจุบัน) | ตอนนี้ตามแผนที่ตกลงกันล่าสุดไหม |
| `baseline_*` (แผนแรก) | หลุดจาก Action Plan ต้นปีไปเท่าไหร่ |

ตัวที่ขึ้นบนการ์ดและตัวนับ Overdue ใช้ **แผนปัจจุบัน** ส่วน baseline เป็นตัวเลข
สำหรับตอนรายงาน ไม่ต้องอยู่บนหน้าแรก

## สิ่งที่คำนวณ ไม่เก็บ

| ค่า | สูตร |
|---|---|
| stage ปิดแล้วหรือยัง | มี task ≥ 1 และไม่มี task ที่ `done_at is null` |
| วันปิด stage | `max(task.done_at)` |
| สถานะ stage | ปิดแล้ว / เลยกำหนด (ถ้าเป็นตัวแรกที่ยังไม่ปิดและเลยวัน) / กำลังทำ (ถึงวันเริ่มแล้ว) / ยังไม่ถึง |
| progress ของ stage | `task ที่เสร็จ / task ทั้งหมด` |
| progress ของ work | ถ่วงน้ำหนักด้วยความยาวของ stage ตามสูตรในสเปกเดิม — **หารด้วยผลรวมความยาวทุก stage ไม่ใช่ความยาวปฏิทิน** ไม่งั้นงานที่มี stage ทับกันจะได้เกิน 100% |
| งานเสร็จแล้ว | ทุก stage ปิดครบ |

ไม่มีคอลัมน์ `status` ไม่มีคอลัมน์ `progress` เหมือนเดิม

## หน้าจอ

หน้างานที่ทำไว้ในรอบ 3 รองรับรอบนี้อยู่แล้วโดยไม่ต้องจัดใหม่ — แท็บ stage,
บรรทัด Timeline, การ์ด Progress และปุ่ม New Task มีที่อยู่ครบ รอบนี้เติมของจริงเข้าไป:

- **รายการ task** ใต้การ์ด Progress ติ๊กเสร็จได้จากตรงนั้น
- **ปุ่ม New Task** ใช้งานได้
- **การ์ด Progress** อ่านตัวเลขจริงแทน 0/0
- **แท็บ** ของ stage ที่ปิดแล้วดูออกจากตัวที่ยังไม่ปิด
- **บรรทัด Timeline** ขึ้นป้ายช้ากี่วันเฉพาะ stage ที่เป็น Overdue ตัวจริง

การติ๊ก task บันทึกทันทีแบบเดียวกับที่รอบ 3 ทำกับ stage ไม่มีปุ่ม Save

## ทางเลือกที่ปัดตกและเหตุผล

| ปัดตก | เพราะ |
|---|---|
| เก็บสวิตช์ `Finished` ไว้คู่กับ task | สองแหล่งความจริงที่ต้องคอยดูแลให้ตรงกัน วันหนึ่งจะไม่ตรง แล้วไม่มีใครรู้ว่าอันไหนถูก |
| ให้ stage ที่ไม่มี task ปิดได้ | จะทำให้ stage ที่เพิ่งสร้างเป็น "เสร็จแล้ว" ทันที ดูหัวข้อ "ปิด stage" |
| คอลัมน์ `frozen_at` และปุ่มแช่แข็ง | Freeze เกิดเองจากกฎ Overdue ทีละอัน ปุ่มที่ต้องจำกดคือปุ่มที่จะลืมกด |
| ช่องให้พิมพ์ว่าเลื่อนกี่วัน | จำนวนวันคำนวณได้จากวันปิดจริงเทียบกับแผน การให้พิมพ์เองคือการเปิดช่องให้พิมพ์ผิด |
| เลื่อนแบบไล่ต่อท้ายตัวก่อนหน้า | ทำลาย stage ที่ตั้งใจให้ทับกัน ดูหัวข้อการเลื่อน |
| ดึงแผนขึ้นเมื่อปิดเร็วกว่ากำหนด | เสร็จก่อนไม่ได้แปลว่าทีมถัดไปว่างรับเร็วขึ้น |
| คำนวณความช้าจากสัดส่วน task ที่เสร็จ | สเปกเดิมปัดไปแล้ว — แม่นกว่าในทางทฤษฎี แต่ผิดทันทีที่ผู้ใช้ไม่ได้ติ๊ก task ตามจริง ความช้าต้องวัดจากวัน ไม่ใช่จากความขยันกรอก |
| task ซ้อน task (subtask) | ยังไม่มีใครขอ และจะทำให้กติกา "ปิดเมื่อครบ" ต้องนิยามใหม่ทั้งชุด |
| กำหนดวันครบกำหนดรายตัวให้ task | ความช้าเป็นเรื่องของ stage วันของ task จะกลายเป็นชั้นที่สองที่ต้องดูแลโดยไม่เพิ่มคำตอบให้ใคร |

## ไม่อยู่ในรอบนี้โดยตั้งใจ

หน้า Timeline เต็ม (รอบ 5) · บล็อก "ช่วงนี้ควรโฟกัส" และ "เพิ่งขยับ" · การเข้ากรุและ
หน้ารายการที่เข้ากรุ · การแสดงตัวเลขเทียบ baseline บนหน้าแรก (เก็บข้อมูลไว้ก่อน
ยังไม่ต้องมีที่ดู) · การมอบหมาย task ให้คนอื่น (แอปนี้ยังมีผู้ใช้คนเดียวต่อบัญชี)

## คำถามที่ยังไม่ตอบ

1. **ติ๊ก task ตัวสุดท้ายแล้วเลื่อนแผนทันทีเลย หรือถามก่อน** — การเลื่อนเขียนทับวันของ
   stage อีกหลายอันในคลิกเดียว ถ้าเงียบเกินไปผู้ใช้จะไม่รู้ว่าเกิดอะไรขึ้น ข้อเสนอ:
   เลื่อนเลยแล้วขึ้นแถบบอก `เลื่อน 4 stage ไป 19 วัน` พร้อมปุ่ม Undo
2. **stage ที่ข้ามไป** — สเปกเดิมบอกว่าไม่ทำก็ไม่ต้องติ๊กเข้ามาแต่แรก แต่ถ้าติ๊กเข้ามาแล้ว
   ค่อยรู้ว่าไม่ต้องทำ ตอนนี้ทางเดียวคือลบ stage ทิ้ง ซึ่งพา task ที่อาจติ๊กไปแล้วหายด้วย
3. **task ที่ยกเลิก** ต่างจาก task ที่เสร็จ แต่ทั้งคู่ไม่ควรค้าง stage ไว้ — ยังไม่มีที่ทาง
